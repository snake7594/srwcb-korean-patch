# v0.11.37 — 프리징 한 부류를 엔진 차원에서 막았습니다

전투 뒤 멈추는 제보(#23 · #24 · #25 · #26)를 파다가, **개별 문안이 아니라 엔진
쪽에 프리징을 부르는 구멍**이 있다는 걸 찾았습니다. 그 구멍을 막았습니다.

---

## 무엇이 문제였나

`F8` 은 문장 안에 런타임 값(이름·숫자 따위)을 끼워 넣는 **치환 옵코드**입니다.
핸들러를 역어셈블하면 이렇습니다(EX `0x80069D60`, 네 실행파일 동일):

```
a2 = W            # 폭. 인자가 0x80 보다 크면 W = 인자-0x80 으로 스크립트에 박힌다
a1 = 길이          # 실제 치환값 길이. 파라미터 링버퍼에서 런타임에 꺼낸다
v1 = a2 - a1
if (v1 != 0) do { *p++ = 0x00; } while (--v1);     # 빈칸 패딩
v1 = a1;  링버퍼에서 a1 바이트 복사
```

`v1` 은 **부호 없는 32비트**로 도는데 **하한 검사가 없습니다.** 치환값이 폭보다
길면 `v1` 이 음수가 되어 `2³² − n` 번 돌면서 RAM 을 0으로 밀어 버립니다.
그 자리에서 게임이 멈춥니다.

v0.11.34 의 유닛 개조 프리징이 정확히 이 경로였습니다. 그때는 원인이 된 문안
하나를 고쳤는데, **구멍 자체는 그대로 남아 있었습니다.**

## 원본 코드가 검사를 빼먹은 게 맞습니다

근거가 **같은 엔진 안에** 있습니다. 링버퍼에 값을 밀어 넣는 **생산자**
쪽(EX `0x8006C088`)은 똑같은 뺄셈 뒤에 `blez` 로 음수를 막습니다.
**소비자만 `beqz`** 입니다.

일본어 원문은 가나가 **반각(글자당 1바이트)** 이라 폭을 넘길 일이 드물어 드러나지
않았을 뿐입니다. 한글은 **전각(글자당 2바이트)** 이라 같은 폭에 들어갈 여지가
절반입니다.

## 어떻게 고쳤나

명령 하나의 opcode 필드만 바꿉니다.

```
beqz $v1, <끝>    ->    blez $v1, <끝>        (0x04 -> 0x06)
```

`a2 >= a1` 이면 동작이 **완전히 같습니다.** 다르게 도는 건 레트일이었다면 멈췄을
경우뿐이라, 잃는 동작이 하나도 없습니다. 명령 길이가 그대로라 주소도 안 움직입니다.

핸들러가 `flags & 8` 로 두 갈래라 실행파일마다 2곳입니다.

| | |
|---|---|
| 컴플리트 박스 | `SECOND.WAR` · `THIRD.WAR` · `EX.WAR` · `TR.WAR` 각 2곳 |
| 단독판 | `SLPS_024.06` · `SLPS_025.30` · `SLPS_025.29` 각 2곳 |

`SLPS_020.70`(런처)에는 텍스트 VM 자체가 없어 해당 없습니다.

이건 문안 하나를 고치는 게 아니라 **아직 못 찾은 것까지 포함해 이 부류 전체를**
막는 안전망입니다.

## 같이 고친 것 — BMESS 외부표

실행파일은 저마다 `BMESS2`/`BMESS3`/`BMESS4` **세 표를 모두** 품고 있는데,
지금까지는 자기 게임 것만 갱신됐습니다(`TR.WAR` 만 예외 — 트레이닝 모드가 세 게임
전투를 다 돌려서 셋 다 필요했습니다).

나머지는 그 게임에서 선택되지 않는 죽은 사본이지만, **표가 스테일이면 전투 메시지
로드가 블록 중간에서 시작해 전투가 그대로 멈추는** 부류입니다(트레이닝 모드에서
실제로 겪었습니다). 실행파일 안에 스테일 표를 하나도 남기지 않도록 9개를 전부
갱신했습니다.

## 게이트

`audit/verify_vm_hardening.py` 를 빌드 검증에 넣었습니다. 배포본에 하한 검사
없는 치환 루프가 **0곳**이어야 하고, 같은 지문이 **레트일에서는 2곳** 나오는지도
함께 확인합니다 — '0곳' 이 '전부 고쳐짐' 이지 '패턴을 못 찾음' 이 아니라는 보증입니다.

## 이번에 확인해서 아니라고 밝혀진 것

허탕도 적어 둡니다. 같은 데를 두 번 파지 않으려고요.

- **놓친 대사 포인터 옵코드가 하나 더 있나** — 아닙니다. 아는 7개 형태는 스테일이
  **0곳**이고, 남은 후보는 전부 그림자였습니다(`0x03 op+1` 226곳은 `B9 03` 224곳의 그림자).
- **풀 안 이벤트 스크립트 참조** — 세 게임 모두 스테일 0건.
- **시나리오 구조가 밀렸나** — 레코드 개수·스크립트 길이가 세 게임 전 시나리오에서
  레트일과 정확히 같습니다.
- **`SLPS_020.70` 의 BMESS 표가 스테일인 게 문제인가** — 그 실행파일에는 텍스트
  VM 이 아예 없습니다(런처). 무해합니다.

## 아직 남은 것

- **대사 앞부분 짤림** — `[0x22D]`(줄 폭)·`[0x22F]`(왼쪽 여백)는 **sticky 전역**이고
  EX 시나리오 레코드에는 이를 세팅하는 `F7` 이 없습니다. 즉 직전에 그려진 다른
  창이 남긴 값을 물려받습니다. 확정하려면 **잘린 대사가 화면에 떠 있는 순간의
  DuckStation 세이브스테이트**가 필요합니다(메모리 카드로는 RAM 을 못 봅니다).
- **#20 엔딩·크레딧·예고편 이미지** — 세이브스테이트 대기.
- **#21 EX 오프닝 인용문** — 자산은 특정했고 프롤로그 글판과 묶어 진행합니다.
