## 원인 — 재조준기가 스크립트 옵코드를 덮어썼습니다

이벤트 스크립트에는 `F0 00 <변위16>` 4바이트 명령(공통 서브루틴 호출)이 아주 많습니다.
그 **변위 바이트가 우연히 대사 포인터 옵코드처럼 보이면**, 포인터 스캐너가 그 자리를
옵코드로 인정하고 **옵코드+2 = 다음 명령**을 변위로 덮어썼습니다.

```
레트일     f0 00 b6 00 | b9 02 63 7a       `b6 00` 은 F0 의 변위
v0.11.38   f0 00 b6 00 | 73 03 63 7a       B9 02 옵코드가 사라졌다
```

하필 레트일 변위 `0x02B9` 가 **레코드 시작을 정확히 겨눠서** 재조준기의 안전 필터도
통과했습니다. 그래서 지금까지 어떤 검사에도 안 걸렸습니다.

| | 훼손 |
|---|---|
| EX | **6곳** (sc1 · sc23 · sc25 ×2 · sc43 ×2) |
| 제3차 | **2곳** (sc36 · sc50) |
| 제2차 | 0곳 |

EX `sc23` 이 볼크루스 전투 시나리오입니다. 그 자리를 밟는 순간 스크립트가 통째로
탈선했습니다.

## 어떻게 잡았나 — 추적 빌드

정적 분석으로는 열한 개 가설을 전부 반증하고도 못 잡았습니다. 그래서 인터프리터
디스패처(`0x80062B5C`)에 훅을 걸어 **스크립트 포인터가 크게 움직일 때마다
(출발 → 목적 · 서브콜 깊이 · 옵코드)를 링버퍼에 남기는 진단 빌드**를 만들었습니다.

멈춘 뒤 세이브스테이트에서 읽은 로그:

```
#28387  sc23+0x1811 -> sc23+0x1A15   (스크립트, 정상)
#28388  sc23+0x1A15 -> 0x8019AA82    ★ sc23 끝을 26,559바이트 넘어감
#28389~ 옵코드 0x00 만 읽으며 프레임당 1바이트씩 기어감
```

옵코드 `0x00` 은 기본 핸들러(`0x800628D0`)로 가고 `return 0x8000` = **다음 프레임까지
양보**만 합니다. 커서와 입력은 **전부 스크립트가 구동**하므로 같이 죽고, 메인 루프는
살아 있어 음악은 계속 납니다 — 제보하신 증상 그대로입니다.

## 수정

`tools/analyze_sce_relocation.py` 의 `iter_pointer_sites` 가 **`F0 00 <변위16>` 의 변위
자리에서 시작하는 후보를 인정하지 않습니다.** 이 함수는 재배치기(`relocate_sce`)와
재조준기(`fix_sce_event_refs`)가 함께 쓰므로 두 경로가 한 번에 고쳐집니다.

수정 후 `sc23 블록+0x1BFC` 는 레트일과 **바이트까지 동일**합니다.
